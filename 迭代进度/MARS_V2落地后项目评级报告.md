# MARS V2 落地后项目评级报告（内部自用视角版）

## 1. 评分前提

本报告基于以下前提做判断：

- `MARS_架构与能力演进建议_V2.md` 与 `MARS_架构与能力演进任务清单_V2.md` 中规划的核心事项已经实现。
- 实现质量不是“功能勉强可用”，而是达到可维护、可测试、可文档化、可复盘的工程标准。
- 当前已明确排除的方向继续排除，不因为没有 Reject Inference、Webhook、二维交互探索、ROI 模拟器而扣分。

如果按“内部风控建模框架”的目标来评价，我对 MARS 的综合评分是：

> **9.1 / 10**

这是一个“已经明显超过普通内部工具，足以作为内部长期复用底座”的分数。

---

## 2. 总体判断

如果 V2 全量高质量落地，MARS 会从“功能已经不少，但内部边界还不够稳”的项目，升级成一个：

- 对项目架构师来说，边界清晰、扩展路径明确的框架；
- 对风控模型同学来说，可复现、可审计、可解释的建模工作台；
- 对业务分析师来说，能直接产出可沟通报告的分析底座；
- 对最终用户来说，上手路径更短、报错更清晰、踩坑成本更低的内部专业工具。

它会非常像一个真正可持续演进的领域框架，而不再只是“把很多风控分析功能放在一个仓库里”。

## 4. 优点

## 4.1 架构层面会变得很像“真正的平台内核”

V2 最值钱的不是多了几个功能，而是内部结构会更像一个可以长期维护的平台：

- `reporting` 与计算逻辑解耦后，视图层不会继续反向污染核心分析链路。
- `compute` 层上提后，表达式驱动内核可以被多个模块复用，减少重复实现。
- `BACKEND_MAP -> registry` 后，模型后端扩展会从硬编码分支升级为可插拔骨架。
- 稳定 API、内部 API、experimental API 分层后，团队会更容易管理兼容性承诺。

这意味着项目不再依赖少数人对“大文件+隐式约定”的熟悉，而是可以靠结构本身支撑协作。

## 4.2 风控建模链路会具备很强的“专业可信感”

如果金额加权评估、Vintage / Swap、schema 契约、run manifest、泄漏防护这些点都落地，MARS 在风控场景里的说服力会明显上一个台阶：

- 不只是能训练模型，还能更完整地解释模型在业务上的表现。
- 不只是能出报告，还能说明报告的口径和复现实验的前提。
- 不只是给一个模型对象，还能给出一套可审计、可回放、可导出的运行产物。

这类能力对内部评审、模型复盘、合规审计、跨团队协作都非常重要。

## 4.3 对不同角色的友好度会明显提高

V2 很大的一个进步，是开始同时照顾四类角色：

- 架构师关心的边界、协议、扩展点、兼容性；
- 模型同学关心的复现性、训练预测一致性、解释性、风险防护；
- 业务分析师关心的口径、别名、切片模板、汇报可读性；
- 最终用户关心的最短路径、预检查、报错清晰度。

这说明 MARS 会从“技术上能做很多事”，走向“团队里不同角色都愿意用、敢用、能说清”的状态。

## 4.4 战略上开始收敛，这是加分项

V2 明确移除了 Reject Inference、Webhook、二维交互、ROI 模拟器等方向，这一点本身是加分的。

原因很简单：

- 这些能力并不是当前 MARS 的主结构矛盾；
- 继续横向铺功能只会稀释重构收益；
- 一个成熟项目需要先建立边界、协议和核心主线，而不是同时满足所有想象空间。

从项目治理角度看，**会做减法** 往往比“能想到很多功能”更稀缺。

## 5. 短板

即便 V2 全量落地，我依然不会继续明显上调分数，因为还有几类短板不会自动消失。

## 5.1 还属于“强框架”，但还需要继续沉淀为“内部标准底座”

V2 会把 MARS 做成一个很强的领域框架，但距离“公司内部默认选型”的程度，还差一层沉淀，例如：

- 不同业务团队是否都能按类似方式组织建模项目；
- 内部自研 backend、指标、报表组件是否能低摩擦接入；
- 是否形成统一模板、最佳实践和扩展样板，而不是继续靠口口相传。

也就是说，V2 会把“框架骨架”做扎实，但“内部标准化网络效应”还需要时间形成。

## 5.2 生产级成熟度仍需要时间证明

很多能力就算做出来，也需要多个真实版本周期来证明：

- 兼容层是否真的能稳定执行；
- manifest、schema、artifact versioning 是否经得住迭代；
- benchmark 和异常分层是否真的减少了回归成本；
- 用户是否真的会按预期走最小可用路径，而不是继续绕开框架。

这类问题不是一次重构可以完全解决的，它们依赖真实项目、真实数据、真实协作摩擦的反复打磨。

## 5.3 易用性会显著变好，但离“内部平台级顺滑”还有距离

V2 会把上手体验拉升一个档次，但还不代表已经达到成熟内部平台那种“新人几乎按文档就能稳定跑通”的程度。

原因在于：

- 风控建模本身就是高认知负担场景；
- 用户仍需要理解样本切分、特征语义、分箱状态、建模配置等概念；
- 即使有 preflight 和最小路径，复杂业务项目仍然会暴露很多领域细节。

所以 V2 的提升更准确地说是：**从“工程工具感较强”进化到“专业工具感较强”**，但还不是“默认无脑好用”的内部平台体验。

## 5.4 业务能力深度仍有继续下探空间

V2 会让 MARS 的风控分析主线很完整，但如果未来对标更高阶平台，仍可能继续补：

- 更丰富的评分卡解释链路；
- 更强的样本追踪与实验管理；
- 更系统的模型治理视角；
- 更统一的跨分析模块指标语义体系。

这些不是 V2 的缺点，而是它在达到 9 分左右后自然暴露出来的下一阶段天花板。

---

## 6. 距离更高分还差哪几步

如果目标是从 `9.1` 进一步提升到 `9.3+`，我认为不是再堆功能，而是把下面几件事做扎实。

## 6.1 把“已实现”继续打磨成“可长期承诺”

重点不是有没有实现，而是能不能在内部稳定承诺 2 到 3 个版本窗口：

- 核心入口、结果对象、artifact / manifest 契约是否真的稳定；
- artifact / manifest / schema 版本是否真的兼容；
- experimental 能力是否能平滑转正或被明确回收。

只有这些承诺真正稳定下来，MARS 才能从“做得不错的项目”变成“内部团队敢长期押注的基础设施”。

## 6.2 把扩展机制从“可插拔”提升到“低摩擦内部扩展”

registry 只是第一步，想继续往上走，更看重下面这些问题：

- 内部 backend 接入文档是否足够清晰；
- 自定义 evaluator / metrics / reporting block 是否有标准扩展协议；
- 是否有最小扩展示例和验收模板；
- 其他内部团队能否在不理解源码细节的情况下完成扩展。

可插拔说明架构合格，低摩擦复用才说明内部平台成熟。

## 6.3 把复现与审计能力做成真正的默认路径

manifest、schema 契约、异常分层、preflight 这些能力，只有在默认路径里被自然使用，才真正值钱。

想继续往上走，需要做到：

- 大多数正式建模流程都会自动生成 manifest；
- 预测流程默认做 schema 检查，而不是靠用户手动开启；
- 关键产物默认带版本与元信息；
- 常见报错能在入口就被拦下，而不是运行半天后失败。

高分项目的一个标志，是“正确做法更容易被自然执行”。

## 6.4 把用户体验从“可用”进一步推向“可信赖”

高分内部平台不只要求用户能跑通，还要求用户在过程中有明显安全感：

- 文档是否让新用户知道从哪条路径开始最稳；
- 报告是否能直接拿去业务会讨论；
- 错误提示是否不需要读源码也能理解；
- 结果对象是否清晰到让用户知道下一步该做什么。

这一步看起来不像硬核架构工作，但它直接决定内部 adoption 的上限。

## 6.5 通过真实项目验证，而不是只靠内部主观判断

最后能不能继续往上走，往往不取决于设计稿有多漂亮，而取决于：

- 是否经历过多种业务线、多个团队、多个数据规模的真实内部使用；
- 是否在几轮版本迭代后仍能保持兼容性和清晰度；
- 是否真正减少了模型项目中的返工、误用和沟通成本。

换句话说，**更高分是“被真实内部使用验证出来”的，不是“规划写得完整就自动得到”的。**

---

## 7. 一句话结论

如果 V2 两份演进文档里的内容都高质量落地，MARS 已经会是一套 **非常强的内部信用风控建模与分析框架**，我会给到 **9.1 / 10**。

它的强项会非常明确：

- 架构边界更稳；
- 风控链路更完整；
- 工程治理更成熟；
- 多角色协作更顺滑。

它还没有继续往更高分走的根本原因也很明确：

- 内部标准化和跨团队复用还需要继续沉淀；
- 长期兼容承诺还需要版本周期验证；
- 用户体验还需从“专业可用”继续打磨到“内部平台可信赖”。

所以最准确的判断不是“V2 做完就封神”，而是：

> **V2 做完之后，MARS 会从一个很有潜力的内部项目，进入真正值得长期投入和持续沉淀的阶段。**
