# MARS 架构基准与新增功能准入原则

## 1. 文档目的

这份文档不是 roadmap，也不是任务清单。
它的作用只有一个：

**为 MARS 后续的重构、扩展和新增功能提供统一的“架构基准”和“准入规则”。**

适用场景：

- 新增一个功能前，先判断应不应该做
- 做一个功能时，先判断应该挂在哪一层
- 重构一个模块时，先判断哪些边界不能再被打破

MARS 的定位是：

**内部自用的信用风控建模与分析框架**

因此判断标准优先看：

- 是否提升内部稳定性
- 是否提升复现性、审计性、可维护性
- 是否贴近真实风控数据链路

而不是优先看：

- 是否适合外部生态
- 是否适合社区插件化
- 是否适合做通用平台宣传点

---

## 2. 架构基准

## 2.1 先分层，再扩展

MARS 的主分层基准如下：

- `compute`：表达式、统计算子、共享缺失语义、物化策略
- `feature`：分箱、筛选、特征级规则
- `modeling`：训练、预测、评估、artifact
- `monitoring`：监控计算、趋势指标、异常检测
- `reporting`：HTML / Excel / plot / 渲染
- `core`：基类、异常、常量、稳定协议

新增能力必须优先挂到已有主层，不允许优先靠“塞进某个大文件”落地。

## 2.2 计算层与展现层必须分离

MARS 的计算结果应该先成为：

- 表
- 结果对象
- 结构化 summary

然后再进入：

- HTML
- Excel
- plot
- 报告模板

禁止新增功能一上来就把计算和展示写死在一起。

## 2.3 共享语义只能有一份

以下底层语义必须集中维护，不能多处各写一套：

- 缺失值语义
- 缺失率统计
- PSI 口径
- 物化策略
- schema 契约

典型例子：

- `Null / NaN / missing_values` 的缺失判断逻辑只能有一套共享底座
- `scanner / detector / profiler / monitoring` 必须复用这套底座

## 2.4 Pandas 可以存在，但必须是白名单

MARS 不是“绝对纯 Polars”项目，但 Pandas 只能存在于明确白名单区域：

- logistic backend
- scorecard export
- report / plot rendering

除此之外，新增核心链路默认优先保持在 Polars / `pl.Expr` 内完成。

## 2.5 高层入口不能反向绑死底层

高层便利接口可以保留，但不能反向成为所有下游能力的底层依赖。

例如：

- `profile_stats` 是高层画像入口
- 它不应该成为 `scanner / detector / monitoring` 的底层计算依赖

正确做法是：

- 抽共享 helper
- 高层入口与下游能力共同复用底层

## 2.6 Public API 要稳，Internal API 可以演进

MARS 必须显式区分：

- 稳定 Public API
- Internal API
- Experimental API

对外稳定入口可以慢一点扩展，但必须稳。
内部实现可以持续演进，但不能假装稳定。

## 3. 新增功能准入原则

## 3.1 先问“是不是主线问题”

一个新功能只有在满足下列至少一项时，才值得进入正式规划：

- 补齐风控主链路中的明显能力缺口
- 显著减少人工重复劳动
- 显著降低误用、返工或排障成本
- 能复用到多个模块，而不是只服务一次性场景

如果只是“看起来高级”或“未来也许有用”，默认不进。

## 3.2 先问“是不是底座已准备好”

如果一个功能依赖的共享底座还没抽出来，默认不直接上功能层。

典型例子：

- 缺失率异常检测前，先统一缺失语义和按期缺失统计底座
- 监控增强前，先统一结构化结果对象
- 导出增强前，先拆 `reporting`

## 3.3 先做检测器，不做裁决器

对数据质量、监控、漂移识别这类能力，MARS 当前阶段优先做：

- 检测器
- 扫描器
- 结构化提示器

不优先做：

- 自动删特征
- 自动阻断流程
- 自动外部处置

例如缺失率异常检测的定位应是：

- 数据质量异常检测器

而不是：

- 自动决定特征生死的裁决器

## 3.4 先结构化输出，再考虑集成外部系统

新增功能第一阶段的目标是：

- 能稳定算
- 能结构化输出
- 能被报告、监控、分析链路复用

不是第一阶段就接：

- Webhook
- 调度平台
- 监控看板
- 审批流

## 3.5 先做内部高频场景，不做想象型扩展

新增功能优先支持：

- 真实业务里高频出现的问题
- 多数据源、缺失、样本切分、评分卡、监控、复现、导出这些内部高频场景

低优先级项包括：

- 为了“看起来完整”的通用平台化功能
- 很少被真实使用的复杂交互能力
- 无明确落地用户的分析炫技功能

## 4. 新功能落地前的 6 个检查问题

任何一个新增功能，在进入正式开发前，至少回答这 6 个问题：

1. 这个功能解决的是主线问题，还是边缘问题？
2. 它应该属于 `compute / feature / modeling / monitoring / reporting` 哪一层？
3. 它是否复用了已有共享语义，而不是重复造轮子？
4. 它是否会让某个大文件继续膨胀？
5. 它输出的是结构化对象，还是又把计算和展示绑死了？
6. 它是否会破坏 Public API，或者新增一个以后很难维护的入口？

如果其中 2 到 3 个问题回答不清，这个功能默认不应直接进入开发。

---

## 5. 当前阶段明确鼓励的方向

- `reporting` 解耦
- 超大模块拆分
- `compute` 共享层上提
- 缺失语义与缺失统计底座抽象
- backend registry 与 adapter 收口
- schema / manifest / artifact versioning
- 泄漏防护、preflight、复现性增强
- 缺失率异常检测这类高价值数据质量检测器

---

## 6. 当前阶段明确不鼓励的方向

- 为了功能完整感继续横向铺很多新模块
- 在高层 API 之外再加更多平行入口
- 把计算逻辑直接塞进报表模板或导出逻辑
- 各模块各自维护一套缺失、PSI、schema 口径
- 为外部生态预留过度泛化的复杂设计
- 在没有共享底座的情况下直接上监控增强或异常检测

另外，下列方向已明确排除，不进入当前和后续规划：

- Reject Inference / 拒绝推断
- 监控阈值触发 Webhook
- 二维特征交互探索
- 通过率-收益模拟器 / ROI
- 单调性增强参数的新增规划

---

## 7. 一句话原则

以后 MARS 每新增一个功能，默认先过这一句：

> **先判断它是不是在巩固框架主线，再判断它是不是只是在继续堆功能。**

如果答案偏后者，就先别做；
如果答案偏前者，再进入任务清单和实施步骤。
